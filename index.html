Plays where a replay overturn took runs off the scoreboard

A home run scores the batter and every runner on base. When MLB's own review text says the call on the field was a home run and the review overturned it, the final play record still lists who actually scored — so the runs removed are arithmetic on the official record:

runs removed = (runners on base + 1 batter) − runs the final record credits

Every row prints those inputs, links to the official play-by-play, and opens the broadcast clip. The same MLB wording (“call on the field was overturned”) also covers reviews that award a home run, and those are listed separately as additions with no run count: the pre-review state needed to quantify them is not kept in the archived feed. Plays where a run could have come off the board but no number can be derived at all are listed as candidates with the reason and the clip — never as a count.

Pending official-scorer rulings

When the official scorer cannot decide at once whether a ball in play is a hit, an error or a fielder's choice, the feed carries the event code os_ruling_pending_primary (or os_ruling_pending_prior for a prior base-running event of the same play) with the registered description “Official Scorer Ruling Pending.” Detection below uses those exact registry values.

The live panel reads MLB's feed straight from your browser. If your browser or network cannot reach statsapi.mlb.com, the panel says so and the harvested history underneath still works.

Every overturned replay review found in the scanned games

Read from reviewDetails on the official play-by-play (isOverturned: true, inProgress: false). Reviews are stored at two levels in that feed — on the play and on the individual pitch/play event — and both are collected here. Each row links to the clip, the official play-by-play and the Gameday page.

When the Official Scorer changed a call — error to hit, hit to fielder's choice

Replay reviews are decided on the field in seconds and say nothing about the scorer's own statistical call. This is the slower, separate record: MLB's official post-game scoring-change bulletin, which states in words that a batter scored on an error was re-scored on a hit or a fielder's choice — and whether the batter's RBI moved with it.

Each row is classified only when the official text names both sides of the change, and the row quotes the exact span that was read. Rows that state no ruling change (an assist, a putout, an earned/unearned reclassification) stay unclassified and are counted separately, never guessed. The totals below are tallies of the entries on file: they are not a base rate and not a probability, because MLB publishes the changes it chooses to publish.

How a batted ball is scored — the 0–100 view

Two numbers are published for every scored play in the committed set:

  • Score (0–100) — the model's probability of its top class for the batted ball (hit, error, fielder's choice, or out). This is the number to read while a ball is in the air and no ruling exists yet.
  • SCI (0–100) — the conditional scoring-impact score: the probability of the ruling actually in force, renormalised over hit / error / fielder's choice. It is shown only where the batter reached, because an out has no hit/error/FC ruling to weigh; elsewhere it reads “—” and is never filled in.

Each row also prints what the rule engine would award the batter under every candidate ruling — the RBI answer to “error or hit?”: an error denies the RBI, a hit or a fielder's choice can credit one (with the Rule 9.04(a)(3) exception where a runner from third would have scored). Where the rule needs a scorer's judgment, the row says so.

What the numbers can and cannot say

The published accuracy below is measured on held-out data by the training scripts in this repository. Where a metric has not been produced, the table says so instead of quoting one.

Correlation study

Point-biserial, Spearman, partial correlation, Cramér's V and mutual information between batted-ball inputs and the four-way outcome. Association is not causation and these are unconditional associations — read docs/CORRELATIONS.md for the method.

Rule 9.04 RBI consequences

An error ruling normally denies the batter an RBI, with one exception: Rule 9.04(a)(3), which the scorer applies when — before two are out — a runner from third would ordinarily have scored. A fielder's choice or a hit can credit an RBI that an error would not. The engine returns a range when the facts the rule needs are missing from the feed, because those are scorer judgments, not data.

How every number on this site is produced

  1. Harvest. A GitHub Actions job (this repository's harvest workflow) reads the official schedule and each game's play-by-play from statsapi.mlb.com, then commits the derived JSON. No human edits it.
  2. Detect. Replay reviews come from reviewDetails; pending rulings come only from the two registry codes (/v1/eventTypes); errors come from the official event codes field_error and error.
  3. Compute. Run removals are arithmetic on the official record and are emitted only when a completed review overturned the call and the final event shows the home run was taken away. Direction is read from that final event — the same wording covers reviews that award a home run, which are published separately with no count.
  4. Capture live. The pending marker is a live state: the archive replaces it with the corrected call, so the live-capture workflow polls in-progress games every 10 minutes during game hours and records each pending state and its resolution in data/capture/pending_live.json.
  5. Cross-check. For every play, the runs implied by the runner movements are compared with the official score delta. Disagreements are published in the harvest metadata rather than smoothed away.
  6. Verify. Three plays with published run-removal values are re-fetched and re-checked on every run; the result is shown in the table below and in the workflow log.
